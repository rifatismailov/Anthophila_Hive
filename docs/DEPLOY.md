# Розгортання Anthophila_Hive на сервері організації

Кожна організація ставить **свій** Hive на свій сервер (Linux + Docker) і керує правилами через веб-інтерфейс.
Програма DocScan на ПК не змінюється: ПК отримують підписані пакети й списки з теки / дзеркала, куди публікує Hive.

## 1. Образ

```sh
git clone https://github.com/rifatismailov/Anthophila_Hive.git && cd Anthophila_Hive
docker build -t anthophila-hive .                                 # DocScan yara за замовчуванням: v1.0.7
docker build --build-arg YARA_DOCSCAN_REF=v1.0.8 -t anthophila-hive .   # інша версія DocScan
```

В образі: `hive`, DocScan `yara` / `yarac` для Linux (форк YARA 4.6 з модулем `docscan`, зібраний з
`rifatismailov/yara-docscan` на тегу), `git`, `bubblewrap`, `python3` (лише щоб імпортувати налаштування наявного
`build_vendor_rules.py`). Працює від користувача `hive` (uid 10001), дані — у томі `/data`.

## 2. Запуск

```sh
mkdir -p deploy/tls && cp /шлях/cert.pem /шлях/key.pem deploy/tls/        # сертифікат сервера організації
docker compose -f deploy/docker-compose.yml up -d
```

HTTPS — обов'язково (паролі, пароль сховища ключів):

| Як | Налаштування |
|---|---|
| сертифікат у Hive | `HIVE_TLS_CERT=/tls/cert.pem`, `HIVE_TLS_KEY=/tls/key.pem` (змонтовано лише на читання) |
| reverse proxy з HTTPS (nginx, Caddy) | `HIVE_BEHIND_PROXY=1`; proxy передає `X-Forwarded-Proto: https` і `X-Forwarded-For` |
| перевірка / перший запуск | `HIVE_SELF_SIGNED=1` — тимчасовий самопідписаний сертифікат у `/data/tls` |

Звичайний HTTP у мережу Hive не відкриває (лише на `127.0.0.1`).

## 3. Перший адміністратор і сховище ключів

```sh
docker compose -f deploy/docker-compose.yml exec hive hive user add --name admin --role admin   # пароль — у терміналі
docker compose -f deploy/docker-compose.yml exec hive hive keystore init                         # пароль сховища ключів
```

Далі все — у веб-інтерфейсі `https://<сервер>:8740/`:

1. **Користувачі** (адміністратор): люди організації з ролями. Кожен у **Профілі** змінює тимчасовий пароль і вмикає
   одноразові коди (TOTP).
2. **Ключі**: пароль сховища вже задано; токени git / релізів — тут же (`hive:<назва>`).
3. **Огляд → новий простір** (видимість, версія, що вже стоїть на ПК, «чотири ока»), **ключ правил і ключ списків**
   у сховищі (`hive:<простір>-rules`, `hive:<простір>-lists`). Публічні частини — на ПК:
   `updater.json` → `extra_public_keys` (правила) і `lists.public_keys` (списки).
4. **Джерела**: дерево правил (напр. `https://github.com/rifatismailov/yara-docscan-rules.git`), **Вендорні** —
   генератор, імпорт критичних правил.
5. **Лабораторія**: набори з `/sets` (том, лише на читання): чисті документи, зразки ШПЗ, документи для критичних
   правил.
6. **Цілі**: тека / UNC (змонтована в контейнер), гілка дзеркала, реліз GitHub / Forgejo, теки списків.

## 4. Ролі й «чотири ока»

| Роль | Може |
|---|---|
| viewer | переглядати все |
| editor | правила, рішення, списки, джерела, тести, збирання кандидатів, лабораторія |
| reviewer | + схвалювати релізи, приймати перевірені спрацювання лабораторії |
| publisher | + підписувати й публікувати |
| admin | + користувачі, ключі, цілі, набори лабораторії, налаштування |

«Чотири ока» (увімкнено для нових просторів): реліз публікує не той, хто його зібрав; у публічну ціль — лише після
схвалення саме цього пакета рецензентом, який його не збирав. Спроби входу: після 5 невдалих — блокування облікового
запису на 15 хвилин; з однієї адреси — не більше 20 спроб за 15 хвилин. Сесія — 12 годин.

## 5. Секрети

Ключі підпису правил і списків, токени — у `/data/keys`, кожен зашифрований паролем сховища (scrypt → AES-256-GCM).
Пароль знають люди (зберігайте його в сейфі організації), не сервер: публікатор вводить його у формі на час
підпису чи публікації, після дії він стирається з пам'яті. Без пароля сховища ключі не розшифрувати — і з резервної
копії теж.

## 6. Пісочниця для наборів лабораторії

Набори скануються DocScan `yara` без прапорів лікування (заборонені в коді) і лише на читання. Додатково Hive
запускає `yara` у пісочниці `bwrap` (без мережі, запис лише в тимчасову теку), якщо вона працює. У Docker зі
стандартним профілем seccomp простори імен користувача заборонені — тоді `bwrap` не стартує, і звіт лабораторії
показує «пісочниця: none» (ізоляцію дає сам контейнер: `read_only`, `cap_drop: ALL`, `no-new-privileges`). Щоб
увімкнути `bwrap`, дайте контейнеру профіль seccomp, що дозволяє `unshare` / `clone` з `CLONE_NEWUSER` /
`CLONE_NEWNET`, або запускайте Hive на хості як службу.

## 7. Резервні копії й оновлення

```sh
docker compose -f deploy/docker-compose.yml exec hive hive backup --out /data/backup-$(date +%F).tar.gz
docker compose -f deploy/docker-compose.yml cp hive:/data/backup-2026-11-22.tar.gz .
# відновлення — у нову теку даних:  hive restore --from backup.tar.gz --data /data-new
```

У копії: БД, git просторів, зашифровані ключі, звіти лабораторії, активи релізів, сховище тестових файлів
(конфіденційні документи — зберігайте копію як дані організації; `--no-blobs` — без них). Копії наборів зі ШПЗ — лише з
`--with-sets`. Кеш джерел не копіюється (завантажиться знову).

Оновлення: новий образ (`docker compose build --pull && docker compose up -d`); дані в томі не змінюються, індекс
бібліотеки старішого формату перебудовується сам.

## 8. Що перевірено, а що — ні

- Перевірено: Hive під Linux (amd64 / arm64) збирається статично; HTTPS, вхід, ролі, TOTP, сховище ключів,
  «чотири ока», резервна копія — тестами й справжнім запуском сервера.
- **Не перевірено в цьому середовищі:** саме збирання Docker-образу (на машині розробки немає Docker) і збирання
  DocScan `yara` для Linux у ньому (`./configure --disable-shared --enable-static`). Перший `docker build` на сервері
  або в CI — обов'язкова перевірка; крок образу сам перевіряє, що `yara` має `--critical-rules`.
