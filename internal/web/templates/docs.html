Документація

Anthophila_Hive — фабрика правил для DocScan: тут організація збирає правила виявлення (YARA), правила критичної інформації й білі / чорні списки, перевіряє їх і публікує підписаний пакет, який служба DocScanUpdater на ПК ставить сама. Програма DocScan на ПК не змінюється.

1. З чого почати

Hive розгорнуто на сервері вашої організації; працюють кілька людей з різними ролями. Типовий порядок:

  1. Адміністратор: пароль сховища ключів, користувачі, простір, ключі підпису, джерела, цілі публікації — розділ 2.
  2. Редактор: правила, рішення, тести, списки, збирання кандидата, лабораторія — розділи 4–9.
  3. Рецензент: переглядає звіт лабораторії й схвалює реліз — 10.
  4. Публікатор: вводить пароль сховища, публікує реліз і списки — 10.
  5. На ПК один раз налаштовують, звідки брати пакети й списки і яким ключам довіряти — 11.

«Чотири ока» (вмикається для простору): реліз публікує не той, хто його зібрав; у публічну ціль — лише після схвалення саме цього пакета рецензентом, який його не збирав. Кожна дія записується в журнал (хто, коли, що).

Вхід: пароль (12+ символів) і за бажанням одноразові коди — Профіль → TOTP (Aegis, FreeOTP, Google Authenticator). Після 5 невдалих спроб обліковий запис блокується на 15 хвилин. Сесія — 12 годин.

2. Перший запуск (адміністратор)

  1. Сховище ключів — Ключі → задати пароль сховища (16+ символів). Запишіть його в сейф організації: ним зашифровано ключі підпису й токени, без нього їх не розшифрувати (і з резервної копії теж).
  2. Користувачі — Користувачі: ім'я, роль, тимчасовий пароль (передайте особисто; людина змінить його в Профілі й увімкне TOTP).
  3. Простір — «+ новий простір» у бічній панелі: назва латиницею, видимість (private — приватні правила й списки; public — лише відкриті джерела), версія, що вже стоїть на ПК (напр. v1.0.0: перша власна буде більшою, інакше ПК її не поставлять), «чотири ока».
  4. Ключі підпису — Огляд → SIGNING KEYS → «Новий ключ»: ключ правил і окремо ключ списків, де зберігати — hive:<простір>-rules / hive:<простір>-lists (сховище Hive). Публічні частини (ed25519:…) — на ПК, розділ 11.
  5. Джерело правил — 3.
  6. Цілі публікації — Огляд → PUBLISH TARGETS → «Додати ціль», розділ 12.
  7. Набори лабораторії — 9.

3. Джерела й вендорні правила

Джерело — git-репозиторій з деревом правил DocScan (як yara-docscan-rules), закріплене на конкретному коміті: збирання завжди бере саме цей коміт, тож будь-який реліз можна відтворити.

  • Додати: Джерела → URL, гілка, (необов'язково) точний коміт.
  • Оновити: кнопка «Що зміниться?» — показує змінені файли правил між закріпленим комітом і новим; «Закріпити» — лише після перегляду.
  • Критичні правила з репозиторію (як docscan-critical): «Імпорт критичних правил» — critical/*.yar потрапляють у простір, документи tests/match і tests/no-match — у сховище Hive (у git — лише sha256).

Вендорні (генератор): правила з публічних джерел (signature-base, Elastic, YARA-Forge …) на закріплених комітах, з відбором кожного правила: відкидаються правила, що не можуть спрацювати на Windows-ПК (ELF, Mach-O, Android, webshell), старі, повільні, з хибними спрацюваннями, дублікати; індикаторні отримують тег docscan_info (повідомляються, але не підвищують вердикт). Результат — байт у байт як у build_vendor_rules.py.

  • Імпорт налаштувань: Вендорні → шлях до build_vendor_rules.py і vendor-selection.txt.
  • Оновити джерело: «що зміниться?» біля джерела — правила додані / змінені / прибрані, файли-кандидати поза переліком, вплив на згенерований набір; «Закріпити» — після перегляду, потім збирання й лабораторія.
  • Звіт генератора і його історія — на сторінці «Вендорні»; на сторінці правила — статус у кожній версії звіту.

4. Бібліотека і рішення

Бібліотека — усі правила простору: з джерела, власні, критичні, відкинуті генератором (з причиною). Пошук — за назвою, файлом, тегом, meta.

Відкинути правило: відкрийте правило → «Рішення» → причина (обов'язково: FP на чистих документах, повільне, дублікат …). Відкинуте правило вирізається з файлу під час збирання; рішення зберігається в git простору (хто, коли, чому); «Знову брати» — скасувати. Правило, на яке посилаються інші, відкинути не можна — збирання про це скаже.

5. Власні правила виявлення

Власні правила → «Знайшли ШПЗ — правило за зразком» або порожній файл. Правило — звичайний YARA 4.x з модулями DocScan (pe, math, docscan …) і зовнішніми змінними filename filepath extension filetype owner.

  • «Перевірити» — компіляція справжнім DocScan yarac, помилки з номером рядка; «Перевірити й зберегти» — файл з помилками не зберігається.
  • Назви — унікальні серед усіх правил виявлення (вони компілюються разом).
  • Тестові файли: на сторінці файлу — «має спрацювати» / «не має», вид (документ / зразок ШПЗ). Зразок ШПЗ лише сканується, ніколи не запускається; зберігається без розширення, лише на читання, поза git. «Прогнати тести DocScan».
  • У пакеті власні правила лежать в org/*.yar і підключаються в кінці file-index.yar.

6. Правила критичної інформації

Третій прохід DocScan: якщо текст документа відповідає критичним правилам, документ потрапляє в чергу E5Search. Правила — в critical/*.yar простору («Вид критичної інформації — правило»).

Текст нормалізований: лише малі літери, між словами рівно один пробіл, без переносів. Пастки кирилиці в YARA (редактор попереджає про кожну):

  1. Квантори рахують байти: кирилична літера — 2 байти. Закінчення до 4 літер — {0,8}, а не {0,4}.
  2. Кирилиця в [...] заборонена — пишіть (д|d) замість [дd].
  3. \b не працює з кирилицею — межа слова: (^| )…( |$|[.,;:!?)]).

Обов'язкова meta: description, category, owner. Назви правил унікальні в усіх файлах critical/ (у Wazuh і в черзі стоїть лише назва). Без import і include. Квантори завжди обмежені.

Пакет правил доступний усім ПК (і може бути публічним): назви внутрішніх проєктів, систем, клієнтів — лише в приватному просторі. Справжні паролі в правила не кладуть ніколи.

Під час кожного збирання всі документи tests/match мають потрапити в чергу, жоден з tests/no-match — інакше релізу немає.

7. Білий і чорний списки

Списки. Запис упізнає файл за path (маска: * у межах теки, ** будь-яка глибина, ? один символ), lnk_target (мережева тека-префікс, куди веде ярлик: \\server\share\App\, не файл) і / або sha256 (можна порахувати із завантаженого файлу — сам файл не зберігається). Кілька полів — файл має збігтися з усіма.

Порядок на ПК: чорний sha256 → HIGH + карантин; білий → не сканується; чорний path / lnk_target → HIGH + карантин; інакше звичайний скан. Білий список не може дозволити цілу теку чи сервер (перевірка — тим самим кодом, що на ПК). Попередження (жовті) — не блокують, але майже завжди помилка: маска без sha256, lnk_target, схожий на файл, той самий sha256 у білому й чорному.

Публікація: «Опублікувати в …» → підтвердження → обидва списки підписуються ключем списків з новим serial (більшим за той, що на цілі — інакше ПК не поставлять).

9. Лабораторія

Кандидат пакета проганяється справжнім DocScan на наборах файлів разом з попереднім релізом на тих самих файлах — видно, що змінилося. Сканування — без прапорів лікування, у пісочниці ОС, якщо вона доступна (бічна панель: sandbox).

Набори (адміністратор, Лабораторія → «Додати набір»): тека на сервері за посиланням або копією. Види: clean (чисті документи організації), malware (зразки ШПЗ), critical-match / critical-no-match, critical-labelled (розмічений набір з expected.tsv), hostile (зламані файли). Позначені набори — обов'язкові перед публікацією.

Додати файли в наявний набір (редактор і вище): Лабораторія → «набір … : додати файли» → обрати один чи кілька файлів (напр. новий зразок майнера .exe у malware). Файли кладуться в теку набору у сховищі Hive — оригінальна тека не змінюється; права лише на читання, файли не запускаються, тільки скануються. Ім'я зберігається (правила дивляться на ім'я й розширення); у звітах такий файл — +added/ім'я. Той самий вміст під тим самим ім'ям — нічого не змінює; інший вміст під наявним ім'ям — відмова (перейменуйте файл). Вже зроблені прогони не змінюються: запустіть прогін ще раз — кеш бачить, що набір змінився. Додане можна прибрати там само; разом з набором прибираються і додані файли. У резервну копію вони потрапляють лише разом з копіями наборів (hive backup --with-sets).

Червоний прогін блокує публікацію. Якщо спрацювання перевірене і правильне — рецензент натискає «прийняти» з причиною; прийняття діє, доки тіло правила те саме. Режими: fast (один прохід yara по теці, ~1 хв на 5 000 документів) і full (процес на файл з --docscan-json, як watcher; ~2–3 хв).

10. Збирання, схвалення, публікація

  1. Зібрати (editor): Релізи → «Зібрати, підписати, перевірити» + пароль сховища ключів. Номер — більший за версію на ПК, усі опубліковані й те, що лежить на цілях.
  2. Hive збирає DocScan-rules.zip точно у форматі DocScan, підписує ключем простору і перевіряє пакет тим самим кодом, що й ПК (R01–R13), плюс тести критичних правил.
  3. Лабораторія для цього пакета (кнопка на сторінці релізу) — зелена або жовта.
  4. Схвалити (reviewer, не той, хто збирав): «Схвалити» + що перевірено.
  5. Опублікувати (publisher): «Опублікувати в …» → ввести номер версії → пароль сховища. Після запису Hive ще раз перевіряє те, що лежить на цілі (і як читають ПК, якщо задано адресу).
перевіркащо означає
R01–R02склад bundle, розміри маніфесту й підпису
R03підпис ключем, якому довіряють ПК; формат маніфесту
R04–R06розмір і sha256 пакета, sha256 кожного файлу, docscan-index.yar у корені
R07версія у VERSION.txt = версія маніфесту (з неї ПК знають, що встановлено)
R08–R09critical/: імена файлів, ≤ 256 файлів і 64 МБ, унікальні назви правил
R10–R11компіляція DocScan yarac / yara --critical-rules
R12версія новіша за ту, що на цілі
R13bundle несе ті самі файли

Відтворити реліз: Налаштування → номер → Hive збирає заново з тих самих комітів і звіряє sha256 кожного файлу з підписаним маніфестом.

11. Налаштування ПК (DocScanUpdater)

Один раз на кожному ПК (інсталятор DocScan або політика) — updater.json:

{
  "mode": "mirror",
  "mirror": { "url": "\\\\server\\docscan\\program" },
  "extra_public_keys": ["ed25519:<публічний ключ правил простору>"],
  "rules": { "mirror": { "url": "\\\\server\\docscan\\rules" } },
  "lists": {
    "url": "\\\\server\\docscan\\lists",
    "public_keys": ["ed25519:<публічний ключ списків простору>"],
    "check_every_hours": 24
  }
}

"mode": "mirror" вимагає й mirror.url — дзеркало самої програми DocScan (як і без Hive); без нього DocScanUpdater не прийме конфігурацію. Правила беруться з rules.mirror.url — теки, куди публікує Hive. У режимах github / marker / off правила беруться з GitHub-релізів (rules.github.repo), тому для своїх пакетів потрібен саме mirror (або ціль release у вашому репозиторії).

  • Публічні ключі — Огляд → SIGNING KEYS (або Ключі). Новий ключ додайте на ПК до першої публікації ним.
  • ПК ставлять лише підписаний пакет / список новішої версії (serial); не стартував watcher з новими правилами — відкат.
  • Ручне встановлення: DocScan-Install.ps1 -Rules DocScan-rules-bundle.zip (bundle — серед файлів релізу).
